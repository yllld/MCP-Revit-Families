# Универсальная детализация: формат и проверка

Инструмент `revit_add_family_details` исполняет явную спецификацию. Он не извлекает формы из PDF самостоятельно и не выбирает реализацию по модели оборудования. Контракт проверяет `core/detail_plan.py`; геометрию строят `detail_geometry.py` и `detail_operations.py` в Revit 2021.

## Запрос

Полный воспроизводимый учебный запрос: [examples/details.dry-run.json](../examples/details.dry-run.json). Его размеры — синтетическое задание, а не данные производителя.

```json
{
  "dry_run": true,
  "spec": {
    "schema_version": 1,
    "details": [],
    "requirements": [],
    "expected_bounds_mm": {"min_mm": [-50, -30, 0], "max_mm": [50, 30, 100]},
    "tolerance_mm": 0.1,
    "source_documents": [],
    "replace_generated_ids": [],
    "accept_scaled_dimensions": false,
    "accept_assumptions": false
  }
}
```

Пустые `details` и `requirements` здесь показывают структуру; для выполнения их необходимо заполнить. Все длины — **миллиметры**, углы вращения — градусы. Координаты относятся к внутреннему началу семейства, не к геодезическим координатам проекта.

`expected_bounds_mm` задаёт минимальную и максимальную XYZ-точки **всей объёмной геометрии семейства**, включая оставленную исходную геометрию. Проверяются все шесть границ: смещённая или недостроенная сборка не пройдёт только потому, что помещается внутри габарита. `tolerance_mm` — допуск численного сравнения, 0,01…100 мм; он не подтверждает точность измерений чертежа. Для точных исходных размеров задавайте небольшой разумный допуск.

`source_documents` содержит пары `file`/`sha256`. Каждый локальный `source.file` должен иметь такую запись. SHA256 проверяется при dry-run и при запросе записи. Получить его можно командой `(Get-FileHash -Algorithm SHA256 -LiteralPath 'C:\BIM\inputs\drawing.pdf').Hash.ToLower()`. Если изменился PDF, сначала пересмотрите размеры и калибровку, затем обновите hash. Само совпадение hash не проверяет правильность прочтения документа.

Для записи подайте `dry_run=false` и `context_token` из последнего dry-run. При изменении активного семейства повторите dry-run. Старые `profile`, `operation`, `receiver_refinement` и другие поля под конкретные изделия не поддерживаются. Неизвестные поля геометрии отклоняются, чтобы ошибочно написанная настройка не пропала незаметно.

## Деталь и покрытие требований

```json
{
  "logical_id": "equipment/body",
  "geometry": {
    "kind": "extrusion",
    "frame": {"origin_mm": [0, 0, 10], "u": [1, 0, 0], "v": [0, 1, 0]},
    "loops": [{"kind": "circle", "radius_mm": 20}],
    "depth_mm": 60
  },
  "accuracy": "dimensioned",
  "source": {
    "source_type": "user_input",
    "reference": "Учебное ТЗ из этого документа",
    "field": "Корпус Ø40, высота 60 мм, основание z=10 мм"
  },
  "material_rgb": [180, 180, 180],
  "fine_only": false,
  "expected_bounds_mm": {"min_mm": [-20, -20, 10], "max_mm": [20, 20, 70]}
}
```

`logical_id` — уникальное инженерное имя до 120 ASCII-символов: буквы, цифры, `_`, `.`, `/`, `-`, начинается с буквы или цифры. Суффикс `/plane` и префикс `presentation/` зарезервированы. Имя не задаёт метод построения и не используется как путь к файлу.

Каждая деталь создаёт одно непустое связное тело. Несвязные части задавайте отдельными деталями. `material_rgb` — условный цвет отображения, не подтверждение марки материала или заводского покрытия. По умолчанию цвет серый, деталь видна на всех уровнях детализации; `fine_only=true` оставляет её только на Fine. Необязательные границы детали проверяются с общим `tolerance_mm`.

В `requirements` перечисляются элементы ТЗ:

```json
[
  {"id": "body", "description": "Корпус Ø40 × 60 на отметке 10 мм", "detail_ids": ["equipment/body"]}
]
```

Каждое требование обязано ссылаться на существующие детали; каждая деталь — присутствовать хотя бы в одном требовании. Пустая ссылка, пропущенная или выдуманная деталь блокирует запись. Полноту перечня требований относительно исходного ТЗ проверяет составитель спецификации: этот контроль не является распознаванием PDF.

## Происхождение размеров

| `accuracy` | Условия |
|---|---|
| `dimensioned` | Прямые размеры: `source_type=direct` или явно заданные пользователем `user_input`. `integration_test` используется только для синтетических тестов |
| `scaled` | Разрешение `accept_scaled_dimensions=true`; `source_type=derived`, `calculation`, `page`, `view`, калибровка |
| `assumed` | Отдельное разрешение `accept_assumptions=true`; `source.reason` объясняет допущение |

Источник требует `field` или `designation` и `file` или `reference`. Конфликтующие источники блокируются; внешний источник требует `origin=external` и `search_authorized=true`. Флаги принятия выставляет составитель по действительному разрешению пользователя, а не автоматически для обхода проверки.

Пример источника для размера по масштабу:

```json
{
  "source_type": "derived",
  "reference": "Чертёж, ревизия 2",
  "origin": "user_provided",
  "field": "Высота верхнего выступа",
  "page": 3,
  "view": "Спереди, ортогональная проекция",
  "calculation": "100 мм / 200 px × 40 px = 20 мм",
  "calibration": {
    "known_mm": 100,
    "known_drawing_units": 200,
    "measured_drawing_units": 40,
    "result_mm": 20,
    "uncertainty_mm": 1
  }
}
```

Проверяется арифметика `known_mm × measured_drawing_units / known_drawing_units`. Калибровка относится к указанному измерению; правильность выбора размерной линии, проекции и перенос результата в координаты проверяет ассистент. Для детали с несколькими снятыми размерами укажите полный расчёт в `calculation`; при различной достоверности частей разделите их. Перспективную картинку нельзя измерять одним плоским масштабом. Значения по масштабу не используются как прямое подтверждение ADSK.

## Система координат детали

`frame` содержит `origin_mm`, единичные взаимно перпендикулярные векторы `u`, `v`. Векторы безразмерные. Для выдавливания и loft направление — `u × v` по правилу правой руки. Для вращения `u` — радиальное направление, `v` — ось вращения.

| Направление выдавливания | `u` | `v` |
|---|---|---|
| +Z | `[1,0,0]` | `[0,1,0]` |
| +X | `[0,1,0]` | `[0,0,1]` |
| −Y | `[1,0,0]` | `[0,0,1]` |

Другие направления, в том числе наклонные, задаются тем же способом. Точка контура `[x,y]` преобразуется в `origin + x*u + y*v`.

## Контуры

| `kind` | Обязательные поля | Особенности |
|---|---|---|
| `rectangle` | `width_mm`, `height_mm` | Центр в начале профиля |
| `rounded_rectangle` | `width_mm`, `height_mm`, `radius_mm` | Четыре настоящие дуги; диаметр скругления меньше обеих сторон |
| `circle` | `radius_mm` | Две полуокружности |
| `ellipse` | `rx_mm`, `ry_mm` | Две полуэллиптические дуги |
| `polygon` | `points_mm: [[x,y], ...]` | От 3 до 256 вершин; последнее ребро замыкается автоматически, первую точку в конце не повторять |
| `curves` | `segments: [...]` | Замкнутая цепь из 2…256 линий/дуг |

Первые четыре контура допускают `offset_mm: [x,y]`, по умолчанию `[0,0]`. Линия: `{"kind":"line","start_mm":[0,0],"end_mm":[20,0]}`. Дуга: `{"kind":"arc","start_mm":[20,0],"end_mm":[0,0],"mid_mm":[10,10]}`; `mid_mm` — точка на дуге. Этот пример из двух сегментов образует полукруг. Конец каждого сегмента должен совпадать с началом следующего, включая замыкание.

Пересечения, касания, вырожденные контуры, слишком короткие дуги и другие ограничения геометрического ядра дополнительно проверяются Revit. Успешный dry-run не гарантирует, что ядро сможет построить тело.

## Операции геометрии

### Выдавливание — `extrusion`

Поля: `frame`, `loops` (1…100 контуров), `depth_mm` (>0). Первый контур — внешний; последующие внутренние контуры задают сквозные отверстия. Не допускайте самопересечений, касания границ и вложенных несвязных островов. Начальная грань находится в `frame.origin_mm`, конечная — на положительной глубине по нормали.

Сначала создаётся обычный `Extrusion`. При отказе, в том числе на фиксации транзакции, вся попытка откатывается. Затем тот же набор контуров передаётся `CreateExtrusionGeometry` и `FreeFormElement.Create`. Причина перехода записывается в `native_fallbacks`. Неудачная геометрия не заменяется коробкой.

### Вращение — `revolve`

Поля: `frame`, `profile`, `angle_deg` (0,1…360). Координаты профиля — `[радиус, высота_вдоль_оси]`. Задавайте замкнутый контур на неотрицательной радиальной стороне; ось — `frame.v`. Профиль можно составить из линий и дуг для аналитических выпуклых крышек. Результат создаётся FreeForm через `CreateRevolvedGeometry`.

### Переход по сечениям — `loft`

Поля: `frame`, `sections` из 2…32 объектов `{"offset_mm":0,"profile":{...}}`. Сечения расположены в параллельных плоскостях по `u × v`; смещения возрастают минимум на 0,5 мм. На каждом сечении — один внешний контур. Через `offset_mm` профиля можно смещать центр сечения поперёк оси. Число/порядок рёбер и совместимость сечений должны позволять Revit построить переход. Результат — FreeForm через `CreateLoftGeometry`; это не универсальный sweep по пространственной траектории.

### Булева операция — `boolean`

Поля: `operation` (`union`, `difference`, `intersection`), `left`, `right`. Оба операнда — полные описания геометрии, а не ID существующих элементов Revit. Например, `difference` вычитает описанный цилиндр из описанного основания. Можно вкладывать операции до глубины 6, всего не более 1000 узлов на запрос. Итог должен быть одним непустым связным телом; иначе операция откатывается. Результат — FreeForm. Вырезы не создают отдельные параметрические Void Forms и не режут произвольные исходные элементы семейства.

В одном запросе допускается 1…250 деталей; модуль численно ограничивает координаты и линейные значения пределом 100000 мм, минимальные основные размеры — 0,5 мм. Реальные пределы Revit могут быть строже. Произвольный Python, mesh, сплайны, текстовые надписи, адаптивные компоненты и автоматические зависимости этим форматом не исполняются.

## Изменение уже созданной геометрии

По умолчанию построение только добавляет формы. Для повторной детализации укажите точные `replace_generated_ids`. В dry-run они должны однозначно соответствовать существующим `GenericForm`, помеченным FamilyMCP. Замена выполняется в той же группе транзакций, что и построение: если новое тело не удалось создать, удалённое возвращается при откате.

Список замен не должен включать исходные пользовательские формы, вспомогательные плоскости или виды. Удаление ограничено выбранными формами и зависимыми внутренними элементами эскиза. Если Revit пытается удалить зависимый размер, коннектор или иной защищённый элемент, операция завершается откатом. Прежние опорные плоскости и параметры сохраняются. Поэтому замена параметрической основы с внешними размерными привязками может быть запрещена; используйте чистый базовый RFA. Оставшиеся служебные плоскости автоматически не очищаются.

Детализация не создаёт Family Parameters, не меняет формулы, GUID, значения параметров, типы или коннекторы. Все новые детализированные формы статические и общие для типов. Для согласованного изменения формы нужна новая спецификация; полноценный flex всей сборки пока не реализован.

## Результаты и критерии приёмки

Резервная копия создаётся **до** группы транзакций через SaveAs; после ошибки активный документ может иметь путь резервной копии. Исходный файл на диске не перезаписывается. После успешной фиксации сохраняется отдельный `Detailed_Family.rfa`. Поля `model_committed`, `saved`, `transaction_group_rolled_back`, `active_rfa_path_after` различают изменение памяти, сохранение и откат. Ошибка сохранения после фиксации не может откатить уже завершённую группу: не повторяйте запись автоматически, сначала проверьте документ и отчёт.

`created_details` содержит метод построения, ID, источник, достоверность, измеренные границы; `assembly_validation` — отклонения шести границ. Четыре ортографических 3D-вида создаются в ориентациях 3D/Front/Right/Top, без отсечения геометрии. PNG предназначены для визуального сравнения, не для измерения в миллиметрах по пикселям. `visual_review_required=true` остаётся в отчёте: автоматического сравнения силуэтов с PDF нет. Отсутствие PNG отражается предупреждением, сохранение RFA от этого не отменяется.

Перед производственным применением проверьте в **отдельном тестовом RFA**:

1. Учебный dry-run должен вернуть `ready=true`, 4 детали, 4 требования и габариты 100 × 60 × 100 мм.
2. Запись должна сохранить отдельный RFA, создать 4 формы и четыре вида. Проверьте два отверстия основания, цилиндр, буртик и переход. Просмотрите каждый PNG, затем откройте сохранённый RFA и повторите аудит.
3. В журнале должны быть подтверждены сохранность ADSK/параметров, исходной геометрии, плоскостей и коннекторов. Исходный файл должен остаться неизменным.
4. Повтор без `replace_generated_ids` должен быть отклонён. Явная замена четырёх созданных форм теми же ID должна сохранить итоговое число тел.
5. В копии запроса задайте неверную ожидаемую границу: построение должно завершиться откатом группы; старые формы должны сохраниться. Проверьте вариант с геометрически недопустимым профилем, который проходит структурный dry-run.
6. Отдельно проверьте native → FreeForm fallback на контуре, который Revit принимает как Solid, но отклоняет как native extrusion. Если обе операции ядра отклонены, ожидается полный откат, а не упрощённая замена.

Новая универсальная реализация имеет офлайн-тесты контракта и управляющей логики. Эти тесты не заменяют живую проверку API. Соответствие LOD350, монтажным интерфейсам и полной исходной форме принимается по конкретному ТЗ после визуальной и размерной проверки.
